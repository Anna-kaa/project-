# Как применять навык

## Когда применять

Задачи вида «для каждого посетителя составить программу дня из каталога
мероприятий», где заданы окно доступности, бюджет, лимит числа событий,
обязательные и запрещённые теги, веса интересов, а правила разбросаны по
нескольким документам разной степени свежести. Не применять к задачам
другого типа (аудит экспериментов, планирование релизов) без адаптации
шагов к их документам.

## Порядок работы

1. **Упорядочить источники по действительности.** Для каждого документа
   определить статус: действующие правила (последняя редакция) — базовые
   ограничения; утверждённые официальные изменения — приоритет над базовой
   версией правил и каталога; персональные специальные условия — приоритет
   над значениями по умолчанию; архивы, черновики и афиши прошлых лет —
   НЕ источники правил, только справка. При противоречии побеждает более
   приоритетный источник.
2. **Построить актуальный каталог.** Применить к базовому каталогу все
   официальные изменения: отмены (событие полностью исключается, но его ID
   запомнить), переносы площадок, изменение цен, новые события.
3. **Этап специальных условий (обязательный, не пропускать).** Найти документ
   специальных условий варианта. Выписать из него КАЖДЫЙ параметр, который он
   задаёт или переопределяет: длительность и окно начала обеда, скорости или
   времена переходов, лимиты на число событий в каких-либо интервалах,
   бюджет, дополнительные запреты. Для каждого параметра:
   - упомянут в спец-условиях → использовать значение оттуда вместо значения
     по умолчанию из правил;
   - не упомянут → использовать значение по умолчанию из действующих правил;
   - не предполагать, что спец-условия совпадают с прошлыми запусками:
     параметры каждый раз читаются заново из документа.
4. **Извлечь данные посетителя:** окно доступности, бюджет, лимит числа
   событий, обязательные события, запрещённые теги, веса тегов. Пропуски
   трактовать честно: отсутствует must_attend — пусто; вес тега не указан — 0.
   Никакие данные не придумывать.
5. **Отфильтровать мероприятия:** оставить только действующие, целиком
   попадающие в окно доступности и не содержащие запрещённых тегов.
6. **Выявить заведомо невозможные случаи ДО перебора:**
   - обязательное событие отменено, отсутствует в каталоге, вне окна
     доступности или содержит запрещённый тег;
   - два обязательных события пересекаются по времени;
   - обязательные события уже нарушают спец-условия (например, лимит на
     число событий, начинающихся в определённое время).
   При обнаружении — вернуть IMPOSSIBLE с конкретной причиной, не подбирая
   «почти подходящую» программу.
7. **Построить и проверить кандидатов.** Для каждой комбинации событий
   (отсортированных по времени начала) проверить построчно:
   - конец предыдущего события ≤ начала следующего;
   - переход между корпусами: время перехода от площадки предыдущего события
     до площадки следующего завершается до начала следующего;
   - число событий: от минимума (обычно 3) до лимита посетителя; повторов ID нет;
   - сумма цен ≤ бюджет;
   - обед: длительность и окно начала — из спец-условий или по умолчанию;
     не пересекается с событиями; целиком внутри окна доступности; если обед
     стоит между двумя событиями, время перехода между их площадками должно
     уложиться в зазор вокруг обеда (обед можно провести на площадке
     предыдущего события);
   - каждое спец-ограничение проверено по его формулировке, а не по памяти.
8. **Оценить и выбрать.** Интерес события = сумма весов тегов посетителя
   для всех его тегов. Выбрать программу с максимальным суммарным интересом;
   при равенстве — с меньшей стоимостью; при равенстве — с лексикографически
   меньшим списком ID. Оптимум не обязан быть доказанным, но каждая проверка
   из шага 7 должна быть реально выполнена.
9. **Самопроверка перед выдачей (каждый пункт прогнать явно):**
   все обязательные события в списке; нет отменённых, запрещённых и
   повторов; для каждой пары соседних событий переход уложился; бюджет и
   лимиты соблюдены; обед корректен по всем пунктам шага 7; каждое
   спец-условие проверено по имени из документа.
10. **Оформить вывод:** JSON-массив, по одному объекту на посетителя, поля
    id, status, event_ids, lunch_start, reason. При невозможности —
    status IMPOSSIBLE, event_ids [], lunch_start null, reason с конкретной
    причиной. Никакого текста вне JSON.

## Обработка ошибок и неопределённости

- События нет в действующем каталоге — не использовать и не изобретать.
- Противоречие между документами — применить приоритет из шага 1 и
  продолжать; в причине не ссылаться на архив.
- Не хватает данных для проверки какого-то условия — не додумывать, указать,
  каких именно данных не хватает.
- Обязательные требования несовместимы — IMPOSSIBLE с объяснением, какие
  именно требования столкнулись.

## Чего не делать

- Не переносить в навык значения из конкретных запусков: параметры
  (лимиты, длительности, пороги) читаются из документов каждого нового
  набора данных.
- Не заменять проверку словом «проверь»: каждый пункт шага 7 — конкретная
  операция сравнения над данными.
